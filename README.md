# WbOzon — ежедневная выгрузка WB и Озон для планирования продаж и производства

Раз в сутки скрипт забирает по API данные Wildberries (кабинет «Агапова») и Озон (кабинет «JUST ME»,
бренды JustMe и PerfectKids) и раскладывает их в папку `data/` в виде csv-файлов и сводки `summary.xlsx`.
Скрипт **только читает данные**: в коде есть только методы получения данных (списки, отчёты, остатки, цены).
Он ничего не меняет в кабинетах. Кабинет «Балянов» не подключён.

## Установка и запуск

```bash
git clone https://github.com/ikentikacore-sketch/WbOzon.git && cd WbOzon
python3 -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                # и вписать ключи
python run.py                                       # ручной запуск, полная выгрузка
python run.py --only wb                             # только WB
python run.py --only ozon                           # только Озон
python run.py --head                                # первые 10 строк каждого файла
python run.py --check                               # сверка за последний закрытый период 16–15
python run.py --pack                                # собрать компактные файлы для чата
python run.py --prices                              # срез цен и комиссий БЖ2/БЖ4/БЖ5/БЖ11 на сегодня
```

После каждой выгрузки собирается `data/for_chat.zip` (~600 КБ) и папка `data/for_chat/`.
Там лежат сгруппированные файлы, которые удобно прикладывать в чат. Полные файлы для этого слишком большие.

Первый запуск выгружает всю историю с 16.10.2025 и занимает ~25 минут: у WB лимит
1 запрос в минуту на статистику и отчёт о реализации, у Озона начисления берутся по одному дню.
Следующие запуски дозаписывают только новые дни и занимают ~10 минут.

### Расписание (06:00 каждый день)

* Linux / macOS: `scripts/install_cron.sh`. Ставит строку в crontab
  `0 6 * * * …/scripts/run_daily.sh`. Время берётся по часам компьютера, поэтому у компьютера
  должен стоять московский часовой пояс.
* Windows: `scripts\install_task_windows.bat` ставит задание в Планировщик.
  Ручной запуск — `scripts\run_now.bat`.

Компьютер или сервер должен быть включён в 06:00.

## Ключи

Ключи лежат в файле `.env` в корне проекта. Файл есть в `.gitignore` и в git не попадает.
Шаблон — `.env.example`.

| Переменная | Что это |
|---|---|
| `WB_TOKEN_AGAPOVA` | токен WB, кабинет «Агапова». Нужны категории **Статистика, Аналитика, Цены и скидки, Финансы** и галочка «Только чтение» |
| `OZON_CLIENT_ID` | Client-Id кабинета «JUST ME» (Настройки → Seller API) |
| `OZON_API_KEY` | API-ключ Озона с ролью только на чтение (например «Аналитика» + «Финансы» + «Товары, только чтение») |
| `TAX_RATE` | необязательно: ставка налога для оценки, например `0.06` |

Токены не пишутся в лог: все тексты ошибок проходят через маскировку (`common.mask`).

### Единые колонки продаж и заказов

`platform, cabinet, date, model, article, size, qty, price_pre_spp, price_after_spp, revenue, status`.
Лист «Продажи по артикулам и размерам» в summary.xlsx группирует по `platform + model + size`
(у WB один артикул встречается в разном регистре, например `pk31-12` и `PK31-12`). Исходные артикулы
перечислены в колонке `articles`.
После них идут колонки конкретной площадки: баркод, nmId/SKU, склад, номер отправления и т.д.

* `date` — `YYYY-MM-DD`, деньги в рублях, числа без пробелов. Разделитель десятичных — точка.
* `qty` всегда положительный. Возвраты и отмены **не вычитаются**, а идут отдельными строками:
  * WB продажи: `status` = `sale` / `return`; WB заказы: `ordered` / `cancelled`;
  * Озон: `delivered` / `cancelled` / `return`, у ещё не доставленных — исходный статус Озона
    (`delivering`, `awaiting_deliver` …).
* `price_pre_spp` — цена после скидки продавца, до СПП (WB `priceWithDisc`, Озон `price` в отправлении).
* `price_after_spp` — сколько заплатил покупатель. WB: `finishedPrice`. Озон: `sale_price` из начисления
  «Выручка» (цена после скидок за счёт Озона, аналог СПП). Пока начисления нет, там цена продавца.
  В WB-продажах отдельно лежит `for_pay` (к перечислению).
* Дата продажи у Озона берётся из начисления выручки: Озон начисляет её в момент доставки, а дату
  доставки FBO в отправлениях не отдаёт. Пока начисления нет, дата продажи равна дате заказа.
* Возвраты Озона — это только `ClientReturn`. Возвраты после отмены или невыкупа (`Cancellation`)
  уже есть в заказах как `cancelled`.
* `revenue` = `price_pre_spp × qty`, то есть реализация до СПП.

### Колонка model

* Озон: размер — число в конце `offer_id` после `_`, пробела, точки или дефиса:
  `БЖ11_42` → `БЖ11` / `42`, `ШЖ1-Ч 128` → `ШЖ1-Ч` / `128`, `ШБ1-Син.146` → `ШБ1-Син` / `146`,
  `ПЮ-1-134-140` → `ПЮ-1` / `134-140`. Число меньше 28 размером не считается (`ШКЮ-1` остаётся моделью).
* WB: артикул продавца (`supplierArticle`/`vendorCode`) — это уже артикул модели, размер лежит в `techSize`.
* Затем модель переводится через **`mapping.csv`** в корне проекта (пример — `mapping.example.csv`):

  ```
  platform,source,model
  Ozon,ШКЮ1-Ч,ШКЮ-1Ч
  ```
  `platform` = `WB`, `Ozon` или пусто (правило для обеих площадок). Сравнение без учёта регистра.
  Пока файла нет, модели только приводятся к верхнему регистру. Модель пересчитывается по всей
  истории при каждом запуске, поэтому новый mapping.csv сразу применяется и к старым строкам.

### Как работает дозапись

Площадки меняют статусы задним числом: отмены, возвраты, выкупы. Поэтому при каждом запуске
перезагружаются последние 30 дней (WB) и 45 дней (Озон), и эти строки в файле заменяются свежими.
Более старые строки не трогаются.

## Методы API

Методы сверены с документацией на 19.10.2026. Сайт dev.wildberries.ru и docs.ozon.ru закрыты
антибот-защитой, поэтому я сверял по OpenAPI-спецификациям WB от 17.10.2026 (репозиторий
`eslazarev/wildberries-sdk`), по каналу «Ozon Seller API notification» и по живым ответам API.

### Wildberries

| Данные | Метод | Лимит |
|---|---|---|
| Заказы | `GET statistics-api /api/v1/supplier/orders` | 1/мин |
| Продажи и возвраты | `GET statistics-api /api/v1/supplier/sales` | 1/мин |
| Отчёт о реализации | `POST finance-api /api/finance/v1/sales-reports/detailed` (`period=weekly`, пагинация по `rrdId`) | 1/мин |
| Остатки на складах WB | `POST seller-analytics-api /api/analytics/v1/stocks-report/wb-warehouses` | 3/мин |
| Остатки FBS | `POST seller-analytics-api /api/analytics/v1/stocks-report/seller-warehouses` | 3/мин |
| Цены и скидки по размерам | `GET discounts-prices-api /api/v2/list/goods/filter` | |

**Замены по сравнению с привычными методами:**
* `GET /api/v1/supplier/stocks` **отключён** (отвечает 404 «This method is deprecated», release note 494).
  Вместо него — `stocks-report/wb-warehouses` и `stocks-report/seller-warehouses`. Они отдают остаток,
  «в пути к клиенту» и «в пути от клиента» по размеру (`chrtId`). Артикул и размер подтягиваются
  по `chrtId` из метода цен, баркод — из заказов/продаж/реализации.
  Важно: WB сейчас отдаёт склады WB одной строкой «Склад WB» (release note 570), без разбивки по складам.
* `GET /api/v5/supplier/reportDetailByPeriod` **отключён** (404, release note 498). Вместо него —
  `finance-api /api/finance/v1/sales-reports/detailed`, поля те же, но в camelCase.
* **Статистика заказов и продаж хранит только 90 дней.** Поэтому:
  * продажи и возвраты старше 90 дней (с 16.10.2025) добираются из детализации отчёта о реализации
    (`source = realization`, дата — `saleDt`);
  * заказы старше 90 дней по размерам WB по API не отдаёт (лента заказов — максимум 31 день).
    В `wb_orders.csv` история начинается с даты первого запуска минус 90 дней и дальше копится каждый день.
* У токена нет категории «Контент», поэтому категорию и бренд WB берём из заказов и реализации
  (`subject`, `brand`), а не из карточек.
* СПП в справочнике WB — значение `spp` из последнего заказа или продажи этого размера.
  Метод цен отдаёт только скидку продавца.

### Озон

| Данные | Метод |
|---|---|
| Отправления FBO | `POST /v3/posting/fbo/list` (v2 отключён 31.08.2026) |
| Отправления FBS | `POST /v4/posting/fbs/list` (v3 отключён 31.08.2026) |
| Возвраты | `POST /v1/returns/list` |
| Остатки по складам/кластерам Озона | `POST /v1/analytics/stocks` |
| Свободно / резерв по товару | `POST /v4/product/info/stocks` |
| Остатки FBS по своим складам | `POST /v2/product/info/stocks-by-warehouse/fbs` |
| Начисления (финансы) | `POST /v1/finance/accrual/by-day` + справочник `POST /v1/finance/accrual/types` |
| Товары, цены, бренд, категория | `/v3/product/list`, `/v3/product/info/list`, `/v4/product/info/attributes`, `/v5/product/info/prices`, `/v1/description-category/tree` |

**Замена:** `/v3/finance/transaction/list` и `/totals` отключены 08.09.2026. Вместо них —
`/v1/finance/accrual/by-day`: один запрос на один день, пагинация по `last_id`. Ответы по дням
кэшируются в `data/raw/ozon_accruals/`, закрытые дни (старше 14 дней) повторно не запрашиваются.
Каждое начисление в `ozon_finance_*.csv` разложено на строки:
* `type_id=sale` «Выручка (продажа по цене продавца)» — `commission.sale_amount`. В колонках
  `seller_price` и `sale_price` лежат цена продавца и цена для покупателя;
* `type_id=commission` «Комиссия за продажу»;
* услуги с числовым `type_id`: логистика, эквайринг, обратная логистика, реклама и т.д.
  Названия берутся из `/v1/finance/accrual/types`.

Сумма строк одного начисления равна его `total_amount`. Если Озон добавит неизвестное поле, разница
попадёт в строку `other` «Прочее». На 19.10.2026 таких строк 0. Отправления и размеры Озон отдаёт
по 100 на страницу (лимит API).

### Лимиты и ошибки

* Все запросы идут через `common.request`. При 429 и 5xx запрос повторяется до 6 раз, пауза берётся
  из заголовка `X-Ratelimit-Retry`/`Retry-After`, иначе растёт от 5 до 120 с. Между запросами
  выдерживаются паузы под лимит метода.
* Каждый шаг (цены, заказы, остатки, …) обёрнут отдельно. Ошибка пишется в `log.txt`, а остальные
  шаги продолжают выполняться. Код выхода 1 означает, что были ошибки.

## Финансы (периоды 16–15)

`wb_finance_YYYY-MM.csv` — строки детализации отчёта о реализации, у которых `rr_date` попадает
в период. Добавлены колонки со знаком (продажа «+», возврат «−»), как в итогах личного кабинета:

| Колонка | Смысл |
|---|---|
| `realization_pre_spp` | реализация до СПП = `retailPriceWithDisc × quantity` |
| `sales` | «Продажа»: WB реализовал товар = `retailAmount` |
| `to_transfer` | к перечислению за товар = `forPay` |
| `commission` | все удержания WB с продажи, кроме эквайринга = `sales − to_transfer − acquiring` |
| `wb_reward_total` | «Вознаграждение Вайлдберриз (ВВ)» с НДС = `vw + vwNds`. Бывает отрицательным: в 2026-03, 2026-04 и 2026-07 WB компенсировал СПП, и к перечислению выходило больше «Продажи» |
| `acquiring` | эквайринг |
| `logistics`, `storage`, `penalty`, `deduction`, `acceptance` | логистика, хранение, штрафы, удержания, платная приёмка |
| `tax` | `sales × TAX_RATE`. В отчётах WB налога нет, это оценка по ставке из `.env` |

Еженедельные отчёты WB (пн–вс) не совпадают с границами 16–15. Поэтому строки делятся по дате
строки `rr_date`, а не по отчёту целиком.

Лист «Финансы» в `summary.xlsx` — итоги по периодам: WB — по колонкам выше, Озон — сумма начислений
по типам плюс продано/возвраты/реализация из `ozon_sales.csv`.

## Срез цен и комиссий для плана (`--prices`)

Команда `python run.py --prices` (или `--prices "БЖ2,ШКЮ-1"`) создаёт файл
`data/prices_commissions_<артикулы>_<дата>.xlsx`. Лист «Цены и комиссии» содержит колонки
Площадка, Артикул, Размер, Цена, Комиссия %, Дата. Лист «Детали» — цену до СПП, СПП, фактическую
цену покупателя, комиссии FBO/FBS/FBW, эквайринг и остатки.

* **WB.** Цена после СПП = цена со скидкой продавца × (1 − СПП). СПП в API цен нет, поэтому берётся
  медиана `spp` по заказам этого артикула за сегодня (если сегодня заказов нет — за 2 дня).
  Комиссия — тариф по предмету из `/api/v1/tariffs/commission`: для склада WB это `paidStorageKgvp`.
* **Озон.** Цена = цена продавца (`marketing_seller_price`/`price` из `/v5/product/info/prices`),
  комиссия — `commissions.sales_percent_fbo` оттуда же.
* **Для расчёта суммы к перечислению.** Комиссию WB считают от цены **до** СПП. Фактически
  к перечислению приходит ≈53,6% от цены до СПП (данные отчётов о реализации за октябрь 2026).
  Если умножить цену после СПП на (1 − 43,5%), сумма к перечислению выйдет примерно на 28% меньше
  реальной. Комиссию Озона тоже считают от цены продавца, а не от цены, которую видит покупатель.

  считаются по отправлениям. Для финансов верны начисления.
* В возвратах дата берётся из `/v1/returns/list` (`return_date`), а в начислениях — дата проводки
  возврата, она обычно на несколько дней позже. Часть возвратов конца периода проводится в следующем.

Сверить с ЛК Озона: «Финансы → Начисления», период 16.09–15.10.2026. Итог должен совпасть с
919 814,64 ₽, выручка «Продажи» — с 3 141 923 ₽ (продажи) и −327 013 ₽ (возвраты).

## Известные ограничения

* Остатки Озона по складам (`scheme=FBO`) — из `/v1/analytics/stocks`. Резерва там нет: резерв —
  в строках `FBO_TOTAL`/`FBS_TOTAL` (по товару, все склады вместе).
* Заказы WB по размерам доступны только за последние ~6 месяцев (сейчас с 26.04.2026), раньше —
  только проданные/возвращённые из отчёта о реализации.
* Склады WB API отдаёт одной строкой «Склад WB», без разбивки по складам. Склады FBS — по складам.
* В `wb_orders.csv` у каждого заказа одна строка: `ordered` (не отменён) или `cancelled`
  (отмена или отказ при получении). Всего заказов = `ordered` + `cancelled`.
